# 정상 트래픽 수집 가이드 (1 PC = 1 고객)

작성: 원유찬 · 2026-10-29

## 왜 바꿨나

기존에는 PC 한 대에서 5~20명을 동시에 띄워서, 웹 로그에서는 IP 하나에 여러 명의 요청이 섞였습니다. IP 기준으로 피처를 만들면 사람 한 명이 아니라 여러 명이 합쳐진 행동을 학습하게 되고, 정상 데이터는 항상 `unique_ua_count = 5`가 되어 모델이 행동 패턴 대신 이 값으로 정상/공격을 구분해 버립니다.

그래서 이제는 **팀원 6명이 각자 PC에서 한 명의 고객을 연기**합니다. PC 한 대가 IP 하나이고, 그 IP가 곧 고객 한 명이 되도록 합니다.

## 실행 방법 (팀원별)

| 팀원 | 명령 |
|---|---|
| 1 | `python generate_benign_traffic.py --member 1 --duration 1800` |
| 2 | `python generate_benign_traffic.py --member 2 --duration 1800` |
| … | `--member` 번호만 3~6으로 바꿔서 실행 |

- `--member N`을 지정하면 계정 `userN@example.com`을 사용합니다. 서로 다른 번호를 써야 같은 계정으로 동시에 로그인하는 일이 생기지 않습니다.
- 기기(User-Agent)는 실행할 때 하나를 무작위로 골라 끝까지 유지합니다. 직접 정하려면 `--device iphone | galaxy | win-chrome | win-edge | mac-safari`를 지정하세요. 팀원끼리 기기를 다르게 고르면 데이터가 더 다양해집니다.
- 한 번 방문하고 나면 15~60초 동안 사이트를 떠났다가 다시 방문합니다. 이 간격은 `--away-min`, `--away-max`로 조정할 수 있습니다.
- 실행 결과로 `ml/data/manifests/benign_member{N}_{IP}_{시각}.csv`에 방문 기록이 남습니다. 각 방문의 시작·종료 시각(UTC)과 페르소나가 들어 있으니 Wazuh 로그와 대조할 때 사용하세요.

## 실행 전 체크리스트

1. **시계 동기화**: Windows 설정 → 시간 및 언어 → "지금 동기화"를 누릅니다. 시각이 틀어지면 30초 단위로 나눈 구간이 PC마다 어긋납니다.
2. **IP 확인**: 배너에 표시되는 `로컬 IP`를 팀 채널에 공유합니다. 정상 IP 목록으로 라벨링할 때 필요합니다.
3. **같은 시간대에 함께 실행**: 6명이 같은 30분 동안 동시에 돌리면 동시 접속자 6명인 상황이 됩니다.

## 웹서버 설정 (1회): Apache 로그에 밀리초 추가

지금 로그는 초 단위라서 요청 간격의 상당수가 0으로 계산됩니다. DMZ 웹서버의 Apache 설정에서 아래처럼 바꿔 주세요.

```apache
LogFormat "%h %l %u [%{%d/%b/%Y:%H:%M:%S}t.%{msec_frac}t %{%z}t] \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\"" combined_ms
CustomLog ${APACHE_LOG_DIR}/shop_access.log combined_ms
```

로그는 `[27/Oct/2026:05:44:13.123 +0000]` 형태로 남고, `01_preprocess.py`가 이 형식을 자동으로 인식합니다. 바꾼 뒤에는 Wazuh 대시보드에서 access 로그가 여전히 정상적으로 디코딩되는지 한 번 확인하세요.

## 로그 가져오기: archives.json에서 직접 추출

OpenSearch 대시보드에서 CSV로 내보내면 **최대 10,000행까지만** 받아집니다. 실제로 `pentagi_session_1026` 파일이 정확히 10,000행이었고, 공격 초반 약 3분이 빠져 있었습니다. 그래서 앞으로는 Wazuh 서버의 `archives.json`에서 직접 추출합니다.

1. `ml/src/원유찬/00_export_archives.py`를 Wazuh 서버(192.168.10.30)로 복사합니다.
2. Wazuh 서버에서 원하는 세션의 시간대(KST)를 지정해 실행합니다.
   ```bash
   sudo python3 00_export_archives.py --start "2026-10-29 14:00:00" --end "2026-10-29 14:30:00" --name user_session_1029_1400-1430
   sudo python3 00_export_archives.py --start "2026-10-29 15:00:00" --end "2026-10-29 15:10:00" --name pentagi_session_1029_1500-1510
   ```
   - 결과 파일은 `/tmp/wazuh_export/<name>.csv`에 저장됩니다. 파일명에 `pentagi`나 `attack`이 들어가면 공격으로 라벨링됩니다.
   - 기본으로 `shop_access.log`와 `app.log`만 추출합니다. WAF의 access.log는 같은 요청을 한 번 더 기록하기 때문에 제외합니다.
   - 실행이 끝나면 출발지 IP 목록이 출력됩니다. 팀원 6명의 IP가 모두 있는지 확인하세요.
   - 지난 날짜(자정에 로테이션된 `YYYY/Mon/ossec-archive-DD.json.gz`)도 자동으로 찾아서 읽습니다.
3. 결과 CSV를 PC의 `ml/data/raw_logs/`로 옮긴 뒤 `01_preprocess.py`를 실행합니다.

## 전처리 실행

```bash
# 파일명으로 라벨링 (파일명에 attack 또는 pentagi가 있으면 공격)
python 01_preprocess.py

# 정상 트래픽과 PentAGI가 한 파일에 섞여 있을 때
#  1) 추출할 때 파일명에 mixed를 넣습니다: --name mixed_session_1029_1400-1430
#  2) 공격 IP와 정상 IP(팀원 6명)를 함께 지정합니다
python 01_preprocess.py --attack-ips 192.168.0.151 --benign-ips 192.168.0.21 192.168.0.22 ...
#  - 두 목록 어디에도 없는 IP(서버 내부 테스트 curl, 다른 사람의 접속 등)는 학습에서 제외됩니다
#  - mixed가 없는 기존 파일은 지금처럼 파일명 기준으로 라벨링됩니다
#  - 주의: 공격 도구를 돌리는 PC에서 정상 트래픽 생성기를 같이 돌리면 IP로 구분할 수 없습니다
```

`session_id`는 이제 `파일명__IP` 형식입니다. 그래서 팀원 6명의 데이터가 각각 별도 세션으로 잡히고, `02_train_rf.py`에서 세션 단위로 학습/검증 데이터를 나눌 수 있습니다.

## 전처리 버그 수정 내역

| # | 문제 | 수정 |
|---|---|---|
| 1 | `interval_mean`/`interval_std`가 실제보다 1000배 작게 계산됨 (pandas가 시각을 마이크로초 단위로 저장하는데 나노초로 가정하고 `/1e9`) | `np.diff(...) / np.timedelta64(1, 's')`로 단위와 관계없이 초로 계산 |
| 2 | access.log와 app.log에 같은 요청이 함께 남는데 둘 다 집계됨 | 파일마다 access → app → OpenSearch 순으로 한 가지 소스만 사용 |
| 3 | 초 단위 타임스탬프이고, 타임존 정보(`+0000`)를 버림 | 밀리초와 타임존을 파싱해서 UTC로 통일 |

기존 정상 로그에 다시 적용한 결과, 정상 데이터의 30초당 요청 수는 453건에서 319건으로 줄었습니다(중복 제거). `interval_mean`은 0.0001초에서 0.09초로 바뀌어 실제 값과 맞게 계산됩니다.
