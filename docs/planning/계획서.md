## 1. 프로젝트 개요

### 1.1 주제

**AI 자율 침투 에이전트(ARTEX)의 Shadow API 접근 탐지: 웹 로그와 OpenAPI 명세를 대조하는 Wazuh 룰 + Grafana 실시간 경고**

### 1.2 한 줄 요약

> 웹서버가 공개한 API 명세(`openapi.yaml`)를 "허용 목록"으로 삼아, Wazuh가 수집한 웹 로그에서 **명세에 없는 API 호출**이 나타나면 위험으로 판정하고 Grafana에 단계별 경고를 띄운다.

### 1.3 배경

- AI 침투 에이전트는 `' OR 1=1` 같은 공격 문자열 대신 **정상 HTTP 문법의 요청**으로 방치된 구버전 API(Shadow API)와 인가 결함(IDOR/BOLA)을 노립니다.
- 이런 요청에는 특수문자나 시그니처가 없어서 방화벽, IPS(Suricata), WAF(ModSecurity CRS), Wazuh 기본 룰셋 모두 정상 트래픽으로 통과시킵니다. 실제로 2026-10-26 사전 공격 실험에서 Wazuh 기본 룰 경보는 0건이었습니다.
- 그러나 Shadow API는 정의상 **"공식 명세에 없는 API"**입니다. 방어자는 숨은 API 목록은 몰라도 **자기가 공개한 API 목록(명세)**은 알고 있습니다. 따라서 "명세 밖 호출"을 잡으면 공격 문자열이 없어도 Shadow API 접근을 확실하게 잡을 수 있습니다.

### 1.4 핵심 가설

> ARTEX가 Shadow API를 찾아 악용하는 과정은 기존 보안 장비(pfSense + Suricata, ModSecurity WAF, Wazuh 기본 룰셋)에서 경보가 0건이지만, OpenAPI 명세 대조 룰은 **명세 밖 API 호출을 빠짐없이 탐지**하고, 응답 코드와 빈도로 **정찰 → 발견 → 악용** 단계를 구분해 Grafana에 1분 이내에 경고를 띄울 수 있다.

## 2. 기획 전환 배경

| 항목 | 이전 기획 (폐기) | 새 기획 |
| :--- | :--- | :--- |
| 탐지 방식 | IP별 30초 창 행동 피처로 Random Forest 이진 분류 | 요청 1건마다 OpenAPI 명세와 대조하는 Wazuh 커스텀 룰 |
| 판정 근거 | 요청 속도, 간격 규칙성, 404 비율 등 통계 | "이 메서드 + 경로가 명세에 있는가" + 응답 코드 + 빈도 |
| 필요한 데이터 | 라벨링된 정상/공격 세션 다수 | 명세 파일 1개 (학습 데이터 없음) |
| 경고 출력 | 오프라인 평가 리포트 | Grafana 실시간 경고 |

**전환 이유**

1. **행동 패턴 분류의 논리적 한계:** 공격 에이전트가 속도를 늦추거나 브라우저처럼 행동하면 행동 통계로는 정상과 구분되지 않습니다. 반대로 정상 데이터는 생성기가 정해진 흐름만 호출해서 `error_404_ratio` 같은 피처가 정답지 역할을 하는 "지름길" 문제가 계속 생겼습니다.
2. **정의와 탐지 기준의 일치:** Shadow API = 명세에 없는 API이므로, "명세 밖 호출"을 탐지 기준으로 쓰면 정의와 판정이 같아집니다. 판정 이유도 바로 설명할 수 있습니다.
3. **이전에 제거한 `shadow_api_ratio` 피처와의 차이:** 그 피처는 방어자가 Shadow API 경로(`/api/v1/`)를 미리 안다고 가정한 정답지 피처였습니다. 새 방식은 숨은 경로를 전혀 가정하지 않고 **방어자가 원래 가진 공개 명세만** 기준으로 씁니다.

## 3. 범위와 성공 기준

### 3.1 범위

| 구분 | 포함 | 제외 |
| :--- | :--- | :--- |
| 인프라 | pfSense(+Suricata) 경계 방화벽, ModSecurity WAF + 웹서버(DMZ), DB 서버(LAN), Wazuh 단일 노드 + Grafana(LAN) | 다중 웹서버 확장 |
| 공격 | ARTEX 자율 침투 세션 (인가된 격리 랩) | 사람의 수동 해킹 |
| 탐지 | `/api/` 아래 모든 요청의 명세 대조, 응답 코드별 단계 분류, IP별 빈도 룰 | 명세에 있는 API 내부의 로직 결함 (예: v2 자체의 BOLA) |
| 출력 | Wazuh 경보 → Grafana 대시보드 + 알림 | Active Response 자동 차단 (선택 과제) |
| 제외 확정 | 머신러닝 분류 모델, 방화벽 L4 로그 수집 | |

### 3.2 사전 확정 성공 기준

> 실험 전에 확정하며, 결과가 기준에 못 미쳐도 사후에 바꾸지 않고 그대로 보고합니다.

1. **기존 장비 미탐 입증:** ARTEX 세션 동안 Suricata, ModSecurity, Wazuh 기본 룰셋에서 Shadow API 접근 관련 경보가 0건일 것.
2. **탐지 누락 0건:** ARTEX가 보낸 명세 밖 `/api/` 요청 중 커스텀 룰 경보가 생성되지 않은 요청이 0건일 것 (로그 전수 대조로 확인).
3. **정상 트래픽 오탐:** 정상 사용자 세션에서 **중간(L2) 이상 경보 0건**. 낮음(L1) 경보는 건수를 그대로 보고합니다.
4. **탐지 시간:** ARTEX의 첫 Shadow API 응답(2xx) 시각부터 Grafana 알림 도착까지 **60초 이내**.
5. **단계 구분:** 각 ARTEX 세션에서 도달한 최고 단계(정찰/발견/악용/대량 유출)를 경고 기록만으로 재구성할 수 있을 것.

## 4. 인프라 아키텍처

> 인프라 구성은 이전 기획과 거의 같습니다. 방화벽은 FortiGate 평가판의 제약(정책 3개, 포트 3개, UTM 미지원) 때문에 **pfSense CE + Suricata**로 바꿉니다. Grafana는 이번에 새로 추가합니다.

### 4.1 구성도

```text
[WAN] 정상 고객(호스트 PC 브라우저) / ARTEX 공격 PC
          │
          ▼
[경계] pfSense CE + Suricata (IDS/IPS)     ※ L4 방화벽 로그는 Wazuh로 수집하지 않음
          │  포트포워딩 8000 → 192.168.20.10:80
          ▼
[DMZ 192.168.20.0/24] WEB 192.168.20.10
          • Apache + ModSecurity(OWASP CRS) + PHP 쇼핑몰(Docker)
          • Wazuh Agent: access.log, app.log, modsec_audit.log
          │ 3306                         │ 1514/1515
          ▼                              ▼
[LAN 192.168.10.0/24]
   DB 192.168.10.20                Wazuh 192.168.10.30
   • MariaDB (최소 권한 계정)        • Manager + Indexer + Dashboard (4.14 단일 노드)
   • Wazuh Agent: general/error log  • ★ Shadow API 탐지 커스텀 룰
                                     • ★ Grafana (Indexer를 데이터 소스로 연결)
```

### 4.2 노드별 역할

| 영역 | 노드 | 역할 | 이번 기획에서의 비중 |
| :--- | :--- | :--- | :--- |
| 경계 | pfSense + Suricata | WAN/DMZ/LAN 분리, NAT, IDS/IPS | 기존 장비 미탐 입증용 |
| DMZ | WEB (+ModSecurity) | 공격 대상 쇼핑몰, WAF | **탐지 원천 로그 생성** |
| LAN | DB | 쇼핑몰 데이터 | 유출 사실 교차 확인용 |
| LAN | Wazuh | 로그 수집, 커스텀 룰 판정, 경보 인덱싱 | **탐지 엔진** |
| LAN | Grafana | 경보 시각화, 알림 발송 | **경고 출력** |

### 4.3 IP 할당

| 대상 | IP | 비고 |
| :--- | :--- | :--- |
| pfSense WAN | VMware NAT `192.168.80.x` | 외부 진입점 |
| pfSense DMZ GW | `192.168.20.1/24` | |
| pfSense LAN GW | `192.168.10.1/24` | |
| WEB | `192.168.20.10` | 외부 8000 → 내부 80 |
| DB | `192.168.10.20` | WEB에서만 3306 허용 |
| Wazuh + Grafana | `192.168.10.30` | Grafana 포트(3000)는 관리용 포트포워딩 필요 |

> VMware 주의사항: VMnet1(LAN), VMnet2(DMZ)의 Host adapter는 반드시 OFF로 둡니다. ON이면 윈도우가 게이트웨이 `.1`을 점유해 충돌합니다 (`인프라_구축_실행가이드_및_작업로그.md` 트러블슈팅 참고).

## 5. 대상 웹서버와 취약점 설계

기준 코드: `shop-web-v2-full`

### 5.1 공식 API (v2, 명세에 등록됨)

`public/docs/openapi.yaml`에 등록된 16개 작업이며, 서버 라우터(`public/api/index.php`)에 등록된 목록과 정확히 일치합니다.

| 메서드 | 경로 | 인증 |
| :--- | :--- | :---: |
| POST | `/api/v2/signup` | |
| POST | `/api/v2/login` | |
| GET, PATCH | `/api/v2/users/me` | 필요 |
| GET | `/api/v2/products` | |
| GET | `/api/v2/products/search` | |
| GET | `/api/v2/products/{id}` | |
| POST | `/api/v2/orders` | 필요 |
| GET | `/api/v2/orders/me` | 필요 |
| GET | `/api/v2/orders/{id}` | 필요 |
| POST | `/api/v2/orders/{id}/cancel` | 필요 |
| GET, POST, DELETE | `/api/v2/cart` | 필요 |
| PATCH, DELETE | `/api/v2/cart/{product_id}` | 필요 |

v2는 JWT 검증, 소유권 확인, 입력값 검증(SQLi, Mass Assignment, 수량 경계값)을 모두 적용했습니다. 사전 모의해킹에서 가격 조작, 권한 주입, SQLi, 경계값 공격을 모두 막았습니다.

### 5.2 Shadow API (v1, 명세와 화면에서 빠짐)

| 메서드 | 경로 | 취약점 |
| :--- | :--- | :--- |
| GET | `/api/v1/users/{id}` | BOLA/IDOR (OWASP API1): JWT 서명과 만료만 확인하고 소유권을 확인하지 않음. 아무 계정의 토큰으로 타인 개인정보 조회 가능 |
| GET | `/api/v1/diagnostics/ping?host=` | OS 명령어 주입 (`shell_exec`) |

- v1은 진입 즉시 유효한 JWT를 요구합니다. 토큰이 없으면 v1 아래 **어떤 경로든 401**을 반환합니다.
- 공격 체인: `v2 회원가입/로그인으로 JWT 확보 → 버전 표기를 바꿔 /api/v1/ 탐색 → users/{id} 순차 열거로 개인정보 수집`.
- `/docs/openapi.yaml`이 인증 없이 공개되어 있어(OWASP API9) 공격자가 v2 구조를 보고 v1을 추론하는 단서가 됩니다.

## 6. 탐지 설계: OpenAPI 명세 대조

### 6.1 판정 원리

```text
[요청 로그 1건]  method, path, status, client_ip
      │
      ├─ path가 /api/로 시작하지 않음 ──────────────▶ 검사 대상 아님
      │
      ├─ 쿼리스트링 제거, 경로 정규화
      │
      ├─ (method, path)가 명세 템플릿과 일치 ─────────▶ 정상 (경보 없음)
      │      예: GET /api/v2/products/42 ↔ GET /api/v2/products/{id}
      │
      └─ 일치하지 않음 = 명세 밖 호출 ──▶ 응답 코드로 단계 판정 ──▶ Wazuh 경보 ──▶ Grafana
```

- **메서드까지 비교합니다.** `GET /api/v2/users/me`는 명세에 있지만 `DELETE /api/v2/users/me`는 명세 밖입니다.
- **경로 템플릿 변환:** `{id}`, `{product_id}`는 `[^/]+` 정규식으로 바꿔서 비교합니다.
- **검사 범위는 `/api/`로 한정합니다.** HTML 페이지, 정적 파일, favicon은 원래 명세에 없으므로 제외합니다.

### 6.2 경보 단계

| 단계 | 조건 | Wazuh 레벨 | 의미 |
| :--- | :--- | :---: | :--- |
| **L1 정찰** | 명세 밖 + 404/405 | 5 | 없는 경로를 찔러보거나(퍼징, 버전 탐색) 명세 경로에 다른 메서드를 시도 |
| **L2 발견** | 명세 밖 + 401/403 | 8 | 숨은 API가 **존재**함을 공격자가 확인 (인증 또는 WAF에 막힘). v1은 토큰이 없으면 어떤 경로든 401 |
| **L3 악용** | 명세 밖 + 2xx | 12 | Shadow API가 **데이터를 응답**함 = 정보 노출 발생 |
| **L3-E 서버 오류** | 명세 밖 + 5xx | 10 | Shadow API에 비정상 입력 주입 시도 |
| **F1 자동화 정찰** | 같은 IP, L1이 30초 안에 20건 이상 | 10 | 자동화 도구의 퍼징 |
| **F2 대량 유출** | 같은 IP, L3가 60초 안에 10건 이상 | 14 | ID 열거로 개인정보 대량 수집 진행 중 |

> 단계는 공격 에이전트의 진행 흐름(정찰 → 발견 → 악용 → 대량 유출)과 그대로 맞습니다. Grafana에서 한 IP가 단계를 밟아 올라가는 모습을 시간축으로 보여줄 수 있습니다.
> 임계값(20건/30초, 10건/60초)은 초기값이며, 정상 세션 측정 후 조정합니다. 조정하면 그 근거를 보고서에 기록합니다.

### 6.3 룰 자동 생성 (명세가 바뀌어도 수동 수정 없음)

명세를 사람이 룰로 옮겨 적으면 둘이 어긋납니다. `openapi.yaml`을 읽어 Wazuh 룰을 만드는 스크립트를 둡니다.

```text
openapi.yaml ──▶ gen_shadow_rules.py ──▶ shadow_api_rules.xml ──▶ /var/ossec/etc/rules/
                  • paths × methods 추출                        ──▶ wazuh-manager 재시작
                  • {param} → [^/]+ 변환
                  • 메서드별 허용 정규식 생성
```

룰 구조 (개념):

1. **기반 룰:** 웹 로그 중 경로가 `^/api/`로 시작하는 요청 (레벨 0)
2. **허용 룰:** 메서드별로 "명세 경로 정규식과 일치"하면 레벨 0으로 종료 (명세 안 = 정상)
3. **명세 밖 룰:** 허용 룰에 걸리지 않은 요청을 상태 코드별로 L1 / L2 / L3 / L3-E로 분류
4. **빈도 룰:** `frequency`, `timeframe`, `same_field(client_ip)`로 F1, F2 생성

- 경보에는 `rule.groups: shadow_api`와 단계 그룹(`shadow_api_recon`, `shadow_api_discovery`, `shadow_api_exploit`, `shadow_api_error`, `shadow_api_recon_burst`, `shadow_api_mass_exfil`)을 붙여 Grafana에서 필터링합니다.
- 검증: `wazuh-logtest`에 명세 안 요청 16종과 명세 밖 샘플 요청을 넣어 기대한 룰 ID가 나오는지 확인합니다.

**구현 (2026-10-30):** `detection/shadow_api/` (사용법은 같은 폴더의 `README.md`)

| 룰 ID | 단계 |
| :--- | :--- |
| 100500 | 기반 (`/api` 요청, 명세 안이면 여기서 종료) |
| 100501~100505 | 명세 밖 판정 (명세에 없는 메서드 / 메서드별 명세 경로 불일치) |
| 100510 / 100511 / 100512 / 100513 | L1 / L2 / L3 / L3-E |
| 100520 / 100521 | F1 / F2 |

> Wazuh 서버에 100200~100203을 쓰는 다른 룰이 있어서 시작 번호를 100500으로 정했습니다 (2026-10-30).

- 경로 비교 규칙은 서버 라우터와 같습니다. 경로 파라미터는 `[^/?]+`, 끝 슬래시와 쿼리스트링은 무시하고, `//api`처럼 슬래시를 겹친 우회도 검사 대상에 넣습니다.
- 생성기의 `test`(파이썬 재현, 36개 항목 통과)와 `replay`(기존 로그 재판정)는 Wazuh 없이 돌아갑니다. 실제 Wazuh에서의 동작은 `logtest`로 최종 확인해야 합니다 (특히 `status` 필드 해석 방식).

### 6.4 예외 목록

정상 시스템이 명세에 없는 API를 불러야 하는 경우(헬스체크 등)를 위해 `shadow_api_allowlist.yaml`을 둡니다. 예외는 사유와 함께 기록하고, 현재 랩 기준으로는 비어 있습니다.

| :--- | :--- | :--- |

## 11. 한계와 확인이 필요한 사항

### 11.1 한계 (보고서에 명시)

- **명세에 있는 API 안의 결함은 탐지하지 못합니다.** 예: v2 자체에 BOLA가 있다면 경로가 명세 안이므로 경보가 없습니다. 본 프로젝트의 범위는 "Shadow API 접근 탐지"입니다.
- **명세가 정확하다는 전제**가 필요합니다. 명세에 빠진 정상 API가 있으면 오탐이 됩니다. 현재는 명세와 라우터가 16개 작업으로 일치하는 것을 확인했습니다.
- OpenAPI 스키마 검증 기능이 있는 API 게이트웨이나 상용 API 보안 제품도 비슷한 일을 합니다. 본 프로젝트는 이를 **별도 장비 없이 기존 SIEM(Wazuh) 로그와 룰만으로** 구현했다는 점을 내세웁니다.
- AI 에이전트인지 사람인지는 구분하지 않습니다. 빈도 룰(F1, F2)은 자동화 여부를 보조로 보여줄 뿐입니다.

### 11.2 확인이 필요한 사항

| 항목 | 내용 | 담당 |
| :--- | :--- | :--- |
| 배포 코드 기준 | `sesac_shop_web_php`(작업 로그상 `shell_exec` 제거, IP 제한 해제)와 `shop-web-v2-full`(RCE, v1 IP 제한 유지) 중 실제 VM에 올릴 코드 확정 | 웹/인프라 |
| v1 IP 제한 | Apache vhost의 `V1_ALLOWED_NET`이 켜져 있으면 WAN의 ARTEX는 Apache 단계에서 403 → `app.log`에 안 남고 `access.log`에만 남음. 허용 여부 결정 | 인프라 |
| Apache 로그 디코딩 | 로그 포맷을 밀리초 포함으로 바꿨으므로 Wazuh 기본 `web-accesslog` 디코더가 그대로 동작하는지 `wazuh-logtest`로 확인 | 탐지 |
| Grafana 위치 | Wazuh 서버 VM에 함께 설치(권장, 6GB RAM) 또는 별도 VM | 인프라 |
| 알림 채널 | Discord, Slack, 이메일 중 선택 | 팀 |
| ModSecurity와 RCE | `diagnostics/ping`에 `;`, `|` 같은 명령 주입 문자를 넣으면 WAF가 403으로 막을 수 있음 → 이 경우 L2로 잡히는지 확인 | 탐지 |
